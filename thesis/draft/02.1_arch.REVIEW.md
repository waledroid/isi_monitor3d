## Summary

The expansion succeeds at its stated register: every subsection (2.1.1–2.1.7)
follows the pattern *architecture properties → "In isiMonitor3d, …"* closing
paragraph, and 2.1.8 explicitly frames each foundation by "the property
exploited." The architecture summaries are technically sound at the level a
journal reviewer will check — DETR set prediction, deformable attention, SDXL's
dual encoders and size/crop conditioning, ControlNet's zero convolutions, the
LoRA parameterization, SAM2's Hiera/prompt/decoder split, and MQTT semantics are
all stated correctly and attributed to the right references. Repo grounding is
excellent: I verified the MqttSink backoff (1–30 s, `reconnect_delay_set`),
retained-QoS-1 zone state (`zone_state_qos=1`, forced `retain=True`), per-class

the full LoRA hyperparameter set and the 0.127 final-loss figure (run
`report.md`), RF-DETR's `dets`/`labels`/`masks` output semantics, and every
accuracy number against T1. Two internal-consistency problems, both newly

## Major concerns

**M1. The NMS-free claim (§2.1.1) contradicts the NMS-billed postprocessing
cost in §3.3/§4.1 — one of them is wrong as written.**
§2.1.1: *"it is trained for end-to-end prediction, so the network emits a final
detection set directly without NMS … the exported graph becomes a pure tensor
program with no data-dependent control flow."* But T5's note (§3.3) and §4.1
bill the CPU-side `detect()` cost to *"letterboxing, fp16 conversion, NMS, and
full-frame mask assembly"*, and the G4 record's method section says the same —
for the **same yolo26n-seg model** §2.1.1 just declared NMS-free. The repo has
both paths: `backbone/detection/postprocess.py` auto-detects the
"YOLO26/YOLOv10-style END-TO-END (NMS-free) seg head" (`_decode_seg_end2end`),
while the fallback dense-head path runs `cv2.dnn.NMSBoxes` (and the deployed
config still carries `iou 0.45`). **Action:** determine which decode path the
benchmarked/deployed yolo26n-seg export actually took. If end-to-end: fix the
T5 note and §4.1 wording ("confidence filtering and mask assembly", not NMS).
If the dense path with NMS ran: §2.1.1's "both changes matter for edge
deployment" paragraph claims an exploited property the deployment does not
exploit and must be rewritten as a family property, not a system property.
Secondary wording fix either way: because this project exports the **raw head**
("no decoding baked into the artifact", §2.1.1), the exported graph never
contained NMS in any YOLO generation — the benefit YOLO26 actually delivers
here is removing NMS from the *application-side* postprocess, not from the
graph. Say that.

**M2. §2.1.8/§2.4 describe TensorRT as an ONNX Runtime execution provider; the
deployed configuration no longer uses it.**
§2.1.8: *"TensorRT is used as such a provider, contributing engine-compiled
speed while the application keeps a single hardware-neutral model file and
interface [23]."* The measurement campaign (G3/G4, 2026-07-20) genuinely ran
the TRT EP, so §3.3 is historically correct — but the lazy TRT-EP was retired
on 2026-07-23, and today's `config/backbone.yaml` points `onnx_path` at
`best.fp16.engine` and `yolo11n-pose-dynamic.engine` (prebuilt native TensorRT
engines via suffix dispatch, per-machine artifacts with sidecars). A grounding
check against the repo at submission time will find the present-tense Methods
description false. **Action (author decision, pick one):** (a) pin the paper
explicitly to the as-measured configuration — e.g., "at the time of the
measurement campaign (July 2026), TensorRT acceleration was provided through
the ONNX Runtime TensorRT execution provider" — and keep T4/T5 untouched; or
(b) update §2.1.8/§2.4 to the native-engine path, which then requires
re-measuring T5 (the native path was benchmarked at ~2.1–2.3× over CUDA EP,
different from T5's 2.6–3.0×). Option (a) is the cheap, honest fix. In either
case, the portability sentence survives if reworded around the artifact: the
*exchanged* file remains the hardware-neutral `.onnx`; engines are locally
derived accelerator caches.

**M3. §2.1.5 duplicates the experiment configuration of §2.6 verbatim, and the
"final training loss of 0.127" is not a defensible quality figure.**
§2.1.5's closing paragraph and §2.6 (line ~315) both state: rank 16, 768 px,
2,000 steps, lr 10⁻⁴, batch 1 with four-step gradient accumulation, 53
photographs. A background subsection should not carry the experiment's
hyperparameter table twice; keep the full set once, in §2.6, and reduce
§2.1.5's grounding to "one rank-16 SDXL adapter per class, trained from a few
dozen photographs (Section 2.6)." Separately, *"reaching a final training loss
of 0.127 (mean over the last 100 steps)"* is grounded in the run's `report.md`
but is not meaningful to a reader: diffusion training loss depends on the
timestep-sampling distribution and loss weighting and is not comparable across
runs, datasets, or implementations — a reviewer will ask what claim this number
supports (none: the adapter's actual evaluation is the §3.4 ablation, as the
text itself says). Drop it.

**M4. §2.1.4 (correctly) says only the depth ControlNet conditions generation;
§2.6 still says Canny maps "constrain image synthesis".**
§2.1.4 is accurate against the repo — `sdxl_controlnet.py` loads only
`diffusers/controlnet-depth-sdxl-1.0`, and Canny is merely one of the
control-map *extractors*. But §2.6: *"DepthAnythingV2 and Canny edge detection
generate complementary control maps used to constrain image synthesis"* — the
Canny maps do not reach the generator. The new subsection makes the older
sentence visibly wrong. Fix §2.6 (e.g., "…generate control maps, of which the
depth maps condition image synthesis; edges serve [state actual use, or delete
Canny from the sentence]").

## Minor concerns

**m1.** §2.1 intro: *"components from five complementary research areas: vision
inference, multi-object tracking, projective geometry, synthetic-data
generation, and edge deployment"* — the enumeration omits messaging/delivery,
yet 2.1.7 is MQTT. Make it six areas or fold delivery into the list.

**m2.** §2.1.7 cites the MQTT 5.0 standard [34] while `MqttSink` (paho-mqtt
`Client` default) speaks MQTT 3.1.1. All features described (QoS, retained,
will, keepalive, wildcards) exist in both OASIS versions, so the citation is
defensible — but state the deployed protocol version once, or cite 3.1.1.
Related register point: the *last-will* feature is described but nothing in the
system uses it (no `will_set` in `MqttSink`); by the author's own
properties-exploited rule, trim it or move it to a "not used here" aside as was
done for SAM2's memory module (which handles this pattern well).

**m3.** §2.1.7: *"keeping subscriber cardinality proportional to the number of
classes, not the number of objects"* — the quantity that scales is **topic**
cardinality, not subscriber cardinality. Fix the noun.

**m4.** §2.1.1 (YOLACT): *"each instance mask is the thresholded linear
combination of the prototypes"* — YOLACT applies a sigmoid to the linear
combination (and crops to the box) before thresholding. "the thresholded
sigmoid of a linear combination of the prototypes" is the accurate short form.

**m5.** §2.1.4: *"duplicates the encoder blocks of the base UNet"* — ControlNet
clones the encoder **and middle** blocks. One word.

**m6.** §2.1.5: two small LoRA points. (i) The paper's update is scaled,
$\Delta\mathbf{W} = \frac{\alpha}{r}\mathbf{B}\mathbf{A}$; omitting the scaling
is a common simplification but cheap to include. (ii) *"the restricted
trainable capacity makes optimization practical on very small datasets"* reads
as a claim of [20], which argues parameter/memory efficiency for LLMs, not a
small-data regularization result — keep the sentence but present it as the
system-side rationale ("which is what makes …practical in our few-dozen-image
regime"), not as cited fact.

**m7.** §2.1.3: *"Diffusion models generate images by inverting a gradual
noising process [32]"* — [32] (DDPM) is the conventional citation, but the
framework originates with Sohl-Dickstein et al. (2015). Optional: add the
origin, or phrase as "in the denoising-diffusion formulation [32]".

**m8.** §2.1.8 geometry: *"a plane in the scene induces an invertible
homography …, so a single calibrated camera suffices for metric localization"*
— (i) invertible only when the camera center is off the plane (fine to leave
implicit); (ii) "calibrated" overstates Mode 1, where the floor homography is
fit from measured correspondences with placeholder intrinsics (§2.3). "a
single camera with a metrically anchored floor homography suffices" covers
both modes accurately.

**m9.** §2.1.1: the *"up to 43 % faster CPU ONNX inference"* figure is a vendor
benchmark from the model's own release documentation. The current attribution
("the release documentation reports") is the right hedge — keep it exactly this
guarded; do not let later edits promote it to an unattributed fact.

**m10.** Register, mild: the opening paragraphs of 2.1.3 (DDPM mechanics:
forward corruption / iterative denoising) and 2.1.7 (pub/sub basics) are the
two spots closest to textbook tone. Both recover in their second paragraphs
and both close grounded, so no rewrite is required — but each could lose one
sentence of pure mechanism (e.g., 2.1.3's "sampling then starts from pure noise
and applies the learned denoiser iteratively" is not a property the system
exploits; the latent-space affordability and text conditioning are).

**m11.** Repo file paths in §2.1 grounding paragraphs
(`backbone/comms/mqtt_sink.py`, `trainer/isidet/configs/train_pallet3_seg_yolo26.yaml`,
`trainer/isiGen/src/stages/masking/sam2_masker.py`, `.../control_maps/`,
`.../scaffolds/`) — all verified to exist, but the repository is private, so
these are unverifiable to journal readers. §3 kept artifact paths in prior
reviews; whatever policy the journal template settles on, apply it uniformly —
§2.1 currently cites more internal paths per page than any other section.

**m12.** Bibliography [29] annotation says the prototype/coefficient decode
lives in `backbone/detection/postprocess.py` — true, and note this same file is
the locus of M1; when M1 is resolved, keep this annotation consistent with
whichever decode path the paper ends up describing.

## Verdict

**Minor revision (with two mandatory harmonizations).** The expanded §2.1
holds the journal-background register the author demanded — every subsection
ends anchored in what isiMonitor3d exploits, and the architecture summaries
would survive a knowledgeable reviewer's accuracy check. But M1 (NMS-free
claimed as exploited vs NMS billed in the measured cost breakdown) and M2
(TRT-EP described in present tense vs the retired-and-replaced deployed
backend) are the kind of internal contradictions that cost credibility with a
referee who reads closely, and both require an author decision, not just
copy-editing. M3/M4 are one-paragraph fixes. The minors are line edits.
